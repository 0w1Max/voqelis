# Horizon Small ONNX — изолированный пилот пунктуации

**Статус:** эксперимент; не является production-изменением.

Кандидат: [Horizon-Labs/punctuation-restoration-small v1.1](https://huggingface.co/Horizon-Labs/punctuation-restoration-small), revision \`ee31fdf\` (2026-10-09). Apache-2.0; ONNX quantized ~= 268 MB, tokenizer ~= 34 MB. Из-за особенностей mmBERT обработчик выбирает предсказанную пунктуацию **с последнего подтокена каждого слова**, не с первого. Текст ASR никогда не заменяется перефразированным выводом.

## Граница эксперимента

- Код: \`tools/horizon_model_fetch.py\`, \`tools/horizon_onnx_probe.py\`.
- Данные: \`/var/lib/voqelis/horizon-onnx-pilot/\` — отдельный каталог с ограниченным доступом, который не используется ботом.
- Загрузка: только \`config.json\`, \`tokenizer.json\`, \`onnx/model_quantized.onnx\` по pinned revision; без \`model.safetensors\`, \`transformers\`, \`torch\` и изменений \`.env\`.
- Загрузчик требует явного \`--accept-download\`, минимум 700MB свободного места, проверяет HTTPS+пределы размеров и записывает SHA256 manifest. Для особо строгого audit необходимо дополнительно сверить digest с авторитетным манифестом релиза (предоставляемый upstream сайт не указывает его в модельной карточке).
- Только короткие непунктуированные русские тексты. При потере/усечении токенов — ошибка вместо частичного вывода. Знаки \`-\` отключены во избежание слияния или искажения слов; время \`13:00\` не превращается в якорь для пунктуации.
- Для сравнения с RUPunct на том же корпусе нужно запускать базовую модель **отдельным** процессом, не держать оба весовых набора одновременно в 2 GB RAM.
- Фраза «Друг общался раздраженно был в своих мыслях» — обязательный пилотный случай. Не принимать обещаний улучшения из общего бенчмарка модели без измерения на нашем материале.

## Выполнение

Из чистой отдельной ветки/после PR approval — без изменений production сервиса:

1. Выполнить \`ruff check --isolated --no-cache --ignore UP017,UP041 src tests\`, \`compileall\`, \`pytest\`.
2. Запустить загрузчик под \`voqelis\`:
   \`PYTHONPATH=src .venv/bin/python -m tools.horizon_model_fetch --dest /var/lib/voqelis/horizon-onnx-pilot --accept-download\`.
3. Запустить оценку с отдельным systemd-run unit: \`MemoryMax=900M\`, \`MemorySwapMax=0\`, \`CPUQuota=50%\`, \`RuntimeMaxSec=180s\`, \`NoNewPrivileges=yes\`, \`PYTHONPATH=/opt/voqelis/src\`; использовать \`-m tools.horizon_onnx_probe --model-dir /var/lib/voqelis/horizon-onnx-pilot\`.
4. В отчёте обязательно сохранить: outputs, p50 latency, peak RSS, exit code, 0 изменённых файлов Git, active voqelis.service.
5. При несовместимости ONNX ops или tokenizer — не заменять production и не выполнять \`pip install\` в общей virtualenv.

**Недостаточно для rollout:** набор из 12 crafted примеров позволяет отсечь кандидата, но не доказывает качество. Нужен слепой ручной gold на 30–50 реальных обезличенных аудио/транскрипциях (comma precision/recall/F1, period F1, boundary split/merge, exact lexical preservation, latency, RSS). Дальше отдельный worker + feature flag и осторожная приёмка в Telegram.


## Фактический результат пилота — 27 октября 2026, Москва

Использовалась независимая worktree `/var/lib/voqelis/horizon-pilot-worktree`; production оставался на `e8721c6ba578644b14c8a5f6751ca1ce7c00e73c`. ONNX `model_quantized.onnx` (268414381 байт), токенизатор и конфигурация скачаны один раз и проверены SHA256; код эксперимента: `8fec6e8401258e811960b55f171a2b467f4cfe02`.

Важные экспериментальные результаты:
- Локальные проверки в worktree: Ruff PASS, pytest 321 PASS. В GitHub CI для того же коммита: Ruff PASS, 364 PASS (число тестов различается вследствие отличия базовой ветки/тестового окружения).
- Horizon загружался 10.814 с, p50 обработки 12 коротких текстов 104.57 мс; пиковый **RSS процесса** 547.6 МиБ.
- Ранее измеренный RUPunct: p50 2.2 мс; пиковый RSS ~138.7 МиБ в отдельном запуске. Это ориентировочное сравнение разных экспериментов, не строго одинаковые условия и не end-to-end latency Telegram.
- Все 12 случаев прошли лексическую проверку, но верная последовательность слов **не означает** верные знаки.

| Входная фраза | RUPunct | Horizon | Интерпретация |
| --- | --- | --- | --- |
| `друг общался раздраженно был в своих мыслях` | `Друг общался, раздраженно был в своих мыслях.` | `друг общался, раздраженно, был в своих мыслях.` | **Обе модели ошибаются** относительно целевого `Друг общался раздражённо, был в своих мыслях.`; Horizon добавляет ещё одну нежелательную запятую |
| `сегодня я закончил работу завтра в девять часов начну новую задачу` | `Сегодня я закончил работу. Завтра в девять часов. Начну новую задачу.` | `сегодня я закончил работу. завтра в девять часов начну новую задачу.` | Horizon правильно устранил ложный разрыв перед `начну` |
| `завтра в 13:00 созвон потом в 14:30 встреча` | `Завтра, в 13:00 созвон, потом в 14:30 Встреча.` | `завтра в 13:00 созвон, потом в 14:30 встреча.` | У Horizon лучше запятые и нет ложной заглавной буквы |
| `завтра с 23:00 до 01:00 читать книгу` | `Завтра с 23:00 до 01:00 Читать книгу.` | `завтра с 23:00 до 01:00 читать книгу.` | У Horizon нет ложной заглавной `Читать` |

При этом текущий Horizon-адаптер **не восстанавливает регистр** и оставляет начало новых предложений с маленькой буквы. Имеет смысл оценивать его семантическую разметку знаков отдельно, но в качестве production drop-in замены RUPunct он не готов.

### Архитектурное решение после пилота

**NO-GO: Horizon не переключать в production.** Его выигрыш на границах некоторых предложений не компенсирует ошибку исходной проблемы, расходы ресурсов и неполное восстановление регистра. Оставить PR экспериментальным/draft. Не добавлять частные исправления запятых для отдельных фраз.

Для «Фактов дня» не делать количество фактов полностью зависимым от вероятностной постановки точек: отдельные голосовые элементы и явная команда/кнопка следующего факта должны оставаться надёжным способом ввода; автоматическое разделение — только предварительное предложение с подтверждением и возможностью редактировать. Прямой приоритет — стабилизация этого UX, а не повторение одинаковых сравнений моделей.

Перед новым выбором модели (локальным либо облачным с opt-in) необходим реальный приватный gold-set из разных синтаксических конструкций; только затем автоматические comma/period precision-recall-F1 и ложные split/merge. Никакие личные тексты не выгружать в публичный репозиторий.
