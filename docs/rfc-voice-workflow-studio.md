# RFC — Voqelis Studio: конструктор голосовых сценариев и таблиц

**Статус:** проектное предложение, без развёртывания. **Цель:** из существующего Telegram-бота Voqelis создать персональный, расширяемый голосовой инструмент. Пользователь настраивает процесс один раз; после этого бот ведёт его по вопросам, сохраняет ответы и собирает документы.

## Главный принцип

**Конструктор описывает данные и сценарий, а не исполняемый код.** Никаких пользовательских Python-скриптов, произвольного SQL, шаблонов с исполнением кода или прямых вызовов внешних API. Любой модуль описывается версионированной, валидируемой конфигурацией. Runtime интерпретирует белый список типов полей и разрешённых действий.

## UX-пример

1. Открыть «⚙️ Конструктор» в Telegram Mini App.
2. «Создать сценарий» → назвать «Факты дня».
3. Добавить три поля: «Событие» (один текст), «Факты» (список предложений), «Ошибочные суждения» (список предложений).
4. Для каждого поля задать голосовой вопрос, ручное редактирование, обязательность и способ заполнения (по одному пункту / несколько предложений).
5. Включить шаг предпросмотра, согласие на сохранение и экспорт DOCX/PDF.
6. «Сохранить шаблон» → «Активировать» → шаблон появляется в списке сценариев бота.
7. При записи бот задаёт вопросы, принимает голос или текст, показывает пункты, позволяет исправлять, подтверждать и экспортировать.

Мастер создания: **Название → Поля → Сценарий записи → Подтверждение → Документ → Превью → Опубликовать**. Доступны готовые пресеты и «создать с нуля». Начать с обычной формы, не с редактора блок-схем.

## Модель конфигурации (иллюстрация, не контракт API)

```json
{
  "id": "facts-diary",
  "version": 1,
  "title": "Факты дня",
  "fields": [
    {"id": "event", "label": "Событие", "kind": "text", "required": true},
    {"id": "facts", "label": "Факты дня", "kind": "list", "itemKind": "sentence", "required": true},
    {"id": "judgments", "label": "Ошибочные суждения", "kind": "list", "itemKind": "sentence", "required": true}
  ],
  "steps": [
    {"fieldId": "event", "prompt": "Расскажи, что произошло", "input": ["voice", "text"]},
    {"fieldId": "facts", "prompt": "Какие факты ты наблюдал?", "input": ["voice", "text"]},
    {"fieldId": "judgments", "prompt": "Какие мысли возникли?", "input": ["voice", "text"]}
  ],
  "reviewBeforeSave": true,
  "exports": ["docx", "pdf_a4", "pdf_mobile"]
}
```

Поля и шаги валидируются по JSON Schema/Pydantic, а действия экспорта — по жёсткому enum. Этот JSON не интерпретируется как программный код.

## Слои архитектуры

```text
Telegram chat / Telegram Mini App (React/TS, mobile first)
        | bot commands, voice, text / signed initData
        v
UI Adapters (aiogram + HTTPS API)
        |
        v
Workflow Runtime (переходы состояний, токены, retries, review, permissions)
        |                         |
        +--> ASR / punctuation ---+--> Input normalization / evidence
        |                         |
        +--> Template Registry ---+--> Versioned schema validation
        |                         |
        +--> Persistence ---------+--> draft / entry / event log
        |
        +--> Export Engine (DOCX, printable PDF, phone-friendly PDF)
        |
        +--> Connectors (later, opt-in only)
```

- Не менять сейчас существующие Planner/Notes/DayFacts; обернуть адаптерами после вертикального прототипа. Planner содержит детерминированные правила времени и конфликтов, не подменяемые произвольными шагами конструктора.
- Мини-приложение — **интерфейс проектирования, просмотра и редактирования**. Бот — удобный голосовой ввод, уведомления и доставка файлов. Оба обращаются к одному Workflow Runtime и хранилищу, а не копируют бизнес-логику.
- Python остаётся бэкендом. Минимальный отдельный HTTPS API (например, FastAPI) обслуживает Mini App; React/TypeScript/Vite — представление. Не делать переход на Node.js вместо существующего Python сервиса.
- Отдельное физическое хранение шаблонов и записей SQLite на первом этапе, WAL и транзакции, версионные миграции. Позже допускается PostgreSQL при появлении многопользовательской нагрузки.
- Draft state / entry / template / template_revision / field_value / audit_operation / export_job — минимальные концепты. Порядок элементов списка должен сохраняться. Никогда не стирать запись из-за смены определения шаблона.
- `user_id` привязывается на сервере по проверенному Telegram initData, не из полей запроса. Срок давности `auth_date`, HMAC/Ed25519 согласно документации Telegram, HTTPS, origin/CORS, ограничения запросов, авторизация на каждом SQL/API запросе.
- Персональные/психотерапевтические записи: приватность по умолчанию; секреты и полные тексты не логировать; шифрованные backup/экспорт по запросу; хранение исходных и отредактированных текстов с provenance; никаких отправок врачу без действия пользователя.
- Сохранять как «Ошибочные суждения» пользовательское имя столбца, **не ставить медицинских диагнозов**, не решать самостоятельно, верны ли мысли. Изменения слов после ASR требуют согласия.
- Права доступа templates / entries / exports: только owner; никакого публичного шаблона с сохранёнными записями. Избегать хранения психологических записей в localStorage браузера.
- Версионированность: активные шаблоны immutable revision. Новая редакция шаблона влияет на новые записи, а прошлые экспортируются по той схеме, в которой создавались.
- Никаких произвольных условий JS/Python от пользователя. В будущем — whitelist операторов if/else, optional steps, repeat sections, confidence/manual-confirm flags.
- Конкурентность: в сессии один активный шаг, optimistic revision / per-user lock, token-bound queued audio, не переносить аудио в новый шаг при изменении интерфейса.

## Ступени разработки

### Этап A — закрепить качество «Фактов дня»
Сценарий из 3 полей с кнопочным выбором/исправлением, сохранением, просмотром и тремя экспортами. Реальные Telegram-тесты после каждого релиза. Добавить корректное удаление выбранного элемента, управление порядком, поддержку одного поля несколькими голосовыми, preview DOCX/PDF; не расширять до конструктора до проверки.

### Этап B — Workflow Core, сначала без Mini App
Обобщить модель формы/повторяемого списка, зарегистрировать встроенный шаблон «Факты дня». Сервис создания черновика и шагов, адаптер старых записей; feature flag и тесты совместимости. Бот диктует по декларативному сценарию.

### Этап C — Telegram Mini App MVP
HTTPS, signature-verified auth, список шаблонов, создание из пресетов, поля text/list/date/number/select, порядок вопросов, предпросмотр. Один пользователь может опубликовать свой шаблон, который бот предлагает на главном экране. Просмотр записей и три экспорта. UI mobile-first.

### Этап D — универсальные сценарии
Условные вопросы из заранее определённого набора, повторяемые группы, вложенные записи, связи с планировщиком через адаптер и подтверждение, категории экспорта. Опциональные AI-подсказки с понятным разделением между «распознать/оформить» и «интерпретировать».

## Нефункциональные требования / gate

- Production VPS baseline: 1 vCPU, 2 GB RAM, 20GB NVMe. Фоновые модели по отдельному процессу и cgroup limits; не размещать дополнительные тяжёлые модели в постоянной памяти.
- p95 ввода/UX и inference измеряются реальными тестами; никаких обещаний «мгновенного» ASR заранее.
- Встроенные и созданные пользователем сценарии работают на одном движке; минимум 2 различных шаблона + 2 пользователя в тестах.
- Restore из резервной копии, схема миграций без потери данных, отказоустойчивость при перезапуске посреди выбора пункта.
- Обязательные проверки: mypy/ruff если используется, compileall, pytest, integration Telegram bot mock, SQLite integrity, Word/PDF render + text extraction, auth negative tests, backup + rollback.
- Feature flags; ни один из экспериментальных сценариев не попадает в production без проверок и одобрения.

## Не включать в MVP

Произвольные плагины, продажу шаблонов, работу с медицинскими картами, автоматическую психотерапевтическую интерпретацию, AI-генерацию сценариев «без проверки», внешнюю синхронизацию, no-code скриптовый редактор и совместные рабочие пространства.


## Запланировано: «Голосовые заметки и напоминания» (Notes Reminders V1)

**Статус:** в backlog, не реализовано; не менять текущие заметки, Planner или production до отдельного этапа.

### Примеры

- Пользователь диктует: «Запиши заметку: идея проекта Voqelis». Бот сохраняет исходный текст, показывает его и даёт изменить.
- Пользователь говорит: «Напомни сегодня в 18:30 начать проект» или «Напомни завтра в 9:00 про эту заметку». Бот уточняет, какую заметку связать с напоминанием, если связь неоднозначна.
- Перед постановкой напоминания пользователь видит точные **дату, время и часовой пояс** и подтверждает действие.
- В назначенный момент бот отправляет сообщение **в личный диалог с Voqelis**, с кнопками «Готово», «Напомнить позже», «Перенести», «Открыть заметку».

### Ограничение Telegram

Bot API позволяет писать в личный чат пользователя, который ранее открыл бота, но не предоставляет боту обычную возможность самостоятельно записывать сообщения непосредственно в пользовательское «Избранное» (Saved Messages). «Избранное» соответствует MTProto-чату пользователя с самим собой (inputPeerSelf). В MVP доставлять напоминания в личный диалог Voqelis; пользователь может переслать их в «Избранное» вручную. Не внедрять userbot, стороннюю пользовательскую сессию или сбор кода авторизации ради этого требования.

Источники: https://core.telegram.org/bots/api#sendmessage и https://core.telegram.org/api/saved-messages .

### Архитектура

- Не дублировать реализацию Notes: отдельная сущность \`reminder\` со ссылкой на \`note_id\` (nullable для напоминания без заметки), \`user_id\`, \`chat_id\`, \`text\`, \`scheduled_at_utc\`, \`timezone\`, \`status\`, \`created_at\`, \`sent_at\`, \`retry_at\`, \`attempt_count\`; индексы по статусу и времени.
- LLM/парсер извлекает пользовательское намерение и дату; детерминированный код разрешает абсолютные/относительные даты, часовой пояс, переход через полночь, DST, прошлое время, неоднозначность и подтверждение. Никаких молчаливых поправок времени.
- Persist-before-ack: сначала записать подтверждённое напоминание в SQLite, затем отвечать «создано».
- Системный планировщик запускается отдельно от ASR очереди, восстанавливает ожидающие записи после рестарта и работает по часам UTC. Время пользователя хранится в timezone-aware представлении.
- Доставка через Telegram Bot API с контролем ошибок, Telegram rate limits, повторными попытками с backoff; после рестарта и при сетевых сбоях возможна неоднозначность доставки, поэтому нужна стратегия дедупликации и явный учёт «возможно отправлено», без ложного обещания строго exactly-once.
- Персональная приватность: не помещать содержимое заметки в журналы; доступ только владельцу; предусмотреть возможность отключить превью на экране блокировки, где это поддерживает клиент Telegram.
- UI: список активных напоминаний, редактирование даты/времени и текста, отмена, связь с заметкой, история отправки. Позже — повторяющиеся напоминания и готовые пользовательские сценарии в Voqelis Studio.
- Критерии качества: 1) доставлено в тестовый личный чат в нужное время; 2) сохранность при перезапуске; 3) прошлое/неоднозначное время не превращается в случайное; 4) два пользователя изолированы; 5) race/cancel/retry тесты; 6) отдельный безопасный rollout и мониторинг.

**Приоритет:** после стабилизации пунктуации и «Фактов дня»; технически совместить со следующим общим Workflow Runtime, не переписывая Planner.
